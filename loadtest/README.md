# loadtest/

Tenants, the OTP side channel and the observer for the k6 load runs.
The k6 scripts themselves live in `loadtest/k6/` and are owned separately;
everything here is what they run *against*.

Full context: `.planning/specs/load-test-spec.md` and `.planning/plans/load-test-plan.md`.

```
loadtest/
├── config/tenants.json          generated by gen_tenants.sh — gitignored
├── odoo_addons/modryn_loadtest/ staging-only OTP capture (NEVER move into addons/)
├── seed/
│   ├── gen_tenants.sh           create N tenants + write tenants.json
│   ├── seed_tenant.py           per-tenant people, catalog, bookings, queue
│   ├── make_gold.sh             freeze one seeded tenant as the reset source
│   └── reset_tenants.sh         restore tenants from gold between stages
└── observe/
    ├── observe.sh               CSV sampler: host, postgres, per-tenant cron
    └── cron_lag.sql             the scheduler-lag query, runnable on its own
```

## Three rules that do not bend

1. **Never run load against `bella`.** It holds live Twilio credentials, so
   `modryn.sms._send_now` takes the Twilio branch for every OTP, booking
   confirmation and waitlist offer instead of logging the body — at ten seconds
   a blocking call.

   **What actually stands there, and what does not.** `gen_tenants.sh` and
   `reset_tenants.sh` both refuse any database carrying a `modryn.twilio.*`
   parameter, but *neither script runs during `k6 run`*. They are pre-flight
   assertions of a property, not a runtime guard. At run time there are two:

   | | what it is |
   |---|---|
   | `guardTenants()` in `k6/lib/session.js` | the only thing that aborts a **run**; fails the test if any tenant's slug or baseUrl contains `bella`. Name-matched, so it does not catch a *different* live boutique. |
   | zero `modryn.twilio.*` on the tenant | the actual mechanism. With no config `_send_now` logs the body and returns `('logged')` — the whole flow exercises at no cost. The seeders' checks are what assert this held at seed time. |

   And one thing that is **not** a guard, though this file used to imply it was:
   the seeded numbers are not deliverable. `+97252TTVVVV` is eleven digits where
   a real Israeli mobile in E.164 is twelve, so Twilio answers them with a 21211
   (invalid `To`) — unbilled, undelivered. It is *not* a carrier prefix and a run
   against a contaminated tenant would not text strangers. That overstatement is
   worth naming because it did damage: it made the Twilio checks feel frightening
   enough to leave alone, and both of them spent their whole life running *after*
   the destruction they were supposed to prevent. `seed_tenant.py`'s
   `assert_phone_scheme()` now pins the digit count so nobody makes the numbers
   real without also re-reading this table.
2. **Stop the Odoo server before `gen_tenants.sh`, `make_gold.sh` or
   `reset_tenants.sh`.** `createdb -T` demands zero connections to the source,
   and `dropdb` blocks on connections Odoo's pool holds open past the request
   that opened them. All three scripts check and refuse rather than half-finish.
3. **`modryn_loadtest` never moves into `addons/`.** Its being outside the
   production `addons_path` is the first of three gates.

## One-time setup

```bash
export MODRYN_DEMO_PASSWORD='pick-your-own'    # the k6 harness needs the same value

# server stopped
./loadtest/seed/gen_tenants.sh 2               # smoke: two tenants
```

Then restart with both settings **on the command line** — do not edit `odoo.conf`:

```bash
./odoo/odoo-bin server -c odoo.conf --http-interface=127.0.0.1 \
  --addons-path="$PWD/odoo/addons,$PWD/addons,$PWD/loadtest/odoo_addons" \
  -d modryn_template,bella,noga,lt01,lt02
```

**Both settings matter, for different reasons.** Without the addons path the
capture module is not loaded and `/loadtest/otp` 404s, so the customer journey
cannot log in. Without `-d` the tenants still serve HTTP perfectly — `dbfilter =
^%d$` routes them off the hostname — and simply never run a cron: the SMS outbox
never drains, reminders never fire, waitlist offers never expire. Measured on
this machine: over 75 s a tenant outside the list went from 137 s to 212 s of
cron lag while one inside went from 102 s down to 16 s. The failure looks like a
slow queue, not like a configuration mistake.

**`-d` on the command line, NOT `db_name` in `odoo.conf`, and that is not a
style preference.** `reset_tenants.sh` and `make_gold.sh` both treat membership
of `odoo.conf`'s `db_name` as the definition of "this is a live tenant, refuse to
drop it" (`db_name_contains`). Writing `db_name = …,lt01,lt02` into the file — as
this section used to instruct — therefore makes the reset workflow refuse the
very tenants it exists to reset:

```
$ ./loadtest/seed/reset_tenants.sh lt01
!! REFUSING: 'lt01' is a LIVE tenant (listed in db_name in .../odoo.conf).
```

`-d` gives the running server the identical database list (crons included) while
leaving `odoo.conf` naming only the three real tenants, so the guard keeps
meaning what it says. Verified both ways on 2026-08-11.

Then, before the first run:

```bash
# server stopped
./loadtest/seed/make_gold.sh lt01              # the reset source
```

Scale up the same way: `./loadtest/seed/gen_tenants.sh 30`, re-cut the gold,
extend `db_name`.

## Between ramp stages

```bash
# server stopped
./loadtest/seed/reset_tenants.sh --all         # every tenant in tenants.json
./odoo/odoo-bin server -c odoo.conf --http-interface=127.0.0.1
```

Measured cost on this host: ~2 s per tenant (a clone plus one psql round trip),
so a 30-tenant reset is about a minute plus the server restart. The reset is
deliberately psql and not `odoo-bin shell` — a registry load is ~13 s per tenant,
which would otherwise *be* the reset budget.

`reset_tenants.sh` re-applies the per-tenant identity the gold overwrote (fresh
`database.uuid`, `web.base.url` and the freeze, company and website names),
renumbers the seeded phones to this tenant's index, and re-asserts both gates.

## While a run is going

Start the observer **before** k6 and stop it (Ctrl-C) **after**, so the ramp-out
tail is captured — that is where a leak shows.

```bash
./loadtest/observe/observe.sh loadtest/results/2026-08-11T09-14_ramp-350
```

| file | contents |
|---|---|
| `pg.csv` | backends by state (gauges) + **per-interval deltas** of commits, rollbacks, tuples, buffer hits/reads, deadlocks, temp bytes |
| `proc.csv` | load average, free/active memory, and the Odoo server's RSS, **true CPU %** and thread count |
| `cron.csv` | per tenant: overdue crons, worst lag, outbox-drain lag, pending `ir_cron_trigger` rows, failed crons, pending outbox, open queue, live bookings |
| `topsql.csv` | top statements by total time — **only if `pg_stat_statements` is installed, and on this host it is not** (see below) |

Knobs: `INTERVAL` (host cadence, default 5 s), `CRON_EVERY` (per-tenant sample
every Nth tick, default 4), `SQL_EVERY`, `TOP_N`.

Two things in there are not obvious and are load-bearing:

* **CPU is a delta of cumulative CPU time, not `ps -o %cpu`.** On macOS that
  column is the average since the process started, so a server that has been up
  an hour reads ~0 % through an entire ramp and the run finds no CPU ceiling
  because it never looked at one.
* **`cron_lag.sql` compares against `now() at time zone 'UTC'`.** `ir_cron.nextcall`
  is `timestamp without time zone` holding UTC; on this host (Asia/Jerusalem) a
  bare `now()` both fails to type-check and, coerced, reports every cron as three
  hours late.

### `pg_stat_statements` is not installed on this box

```
$ psql -d postgres -tAc "select count(*) from pg_extension where extname='pg_stat_statements'"
0
```

Which means **this campaign currently has no query-level evidence**: every claim
it makes about *which statement* dominates — the board rebuild, the slot scan,
the variant search behind `/floor/finish` — rests on wall-clock timings only.
`observe.sh` used to write a header-only `topsql.csv`, which reads exactly like
"the run found no slow queries". It now writes no CSV at all, prints the absence
in the terminal, and drops a `topsql.MISSING.txt` into the results directory,
where whoever opens the numbers a week later is actually looking.

Enabling it needs a preload, so it cannot be switched on for one session:

```bash
psql -d postgres -tAc "show config_file"        # find postgresql.conf
# add:  shared_preload_libraries = 'pg_stat_statements'
brew services restart postgresql@16
psql -d postgres -c "CREATE EXTENSION pg_stat_statements"
```

`deploy/postgresql/tuning.conf` already sets the preload for production; this is
only about the local machine. Reset the view **before each run** —
`SELECT pg_stat_statements_reset()` — because it is cumulative since the last
reset, so without it a run's top statements are diluted by every seed, every
`verify.sh` and every prior stage.

Cron lag is a first-class metric, not a curiosity: Odoo's scheduler makes roughly
one pass per database per 60 s and walks databases **serially**, with
`max_cron_threads = 2` shared across the fleet. At 30 tenants that ceiling is the
one that bites first.

## `modryn_loadtest` — reading an OTP back

Customer login is phone + SMS code, and the code is stored as an HMAC-SHA256
digest salted with the database secret (`modryn_portal/models/otp.py`). There is
no reverse, and that is correct — so the harness gets a side channel instead.

```
GET /loadtest/otp?phone=<E.164>&secret=<S>   ->  200 {"code":"123456"}
```

**Three gates.** All must hold or the route is a 404 and nothing is captured:

| gate | key |
|---|---|
| the module is in `addons_path` at all | `loadtest/odoo_addons`, which production never has |
| capture is switched on, per database | `ir.config_parameter modryn.loadtest.enabled = '1'` |
| the caller knows the secret | `ir.config_parameter modryn.loadtest.secret`, compared with `hmac.compare_digest` |

Every refusal returns the **same 404** — wrong secret, flag off, unknown number,
no live code — so probing the route tells you nothing about which gate you failed
or whether the module exists. Two config keys rather than one means a *mistaken
install* is inert: present, installed, and still capturing nothing.

### Two details that were found by testing, not by reading

**It overrides `_send_now`, not `send`.** Sends route `send -> _send_now` for the
synchronous callers (OTP, the 24 h reminder) and
`send_async -> outbox -> cron drain -> _send_now` for the rest (booking
confirmations, waitlist offers). `_send_now` is the only place all traffic
converges; hooking `send` would miss every queued message.

**It picks the code by HMAC, not by position.** The first version returned the
newest standalone 6-digit run in the newest message, and it was wrong twice over:

* the customer journey books *before* it logs in, and the confirmation travels
  through the outbox, so it can be delivered **after** the synchronous OTP and win
  a newest-first scan;
* and that confirmation carries a booking link whose access token
  (`/b/24-09d7260700cfdc8f0d261165`) ends in a standalone 6-digit run — so the
  route returned `261165` for a real code of `098381`.

Matching every candidate against `modryn.otp.code._hash` means the route cannot
return a wrong code at all: if it answers, the answer verifies. It reads nothing
back out of the hash, so the stored codes stay one-way exactly as designed.

## What the seeder puts in a tenant

`seed_tenant.py` is parameterised by `MODRYN_TENANT_INDEX` and works for any
slug. (`scripts/seed_staff.py` cannot be used: it is a dict keyed by slug with
entries only for `bella` and `noga`, so `PEOPLE['lt07']` raises `KeyError` and
kills the shell mid-loop.)

| | count | logins |
|---|---|---|
| owner | 1 | `owner` — reuses `base.user_admin`, so no second internal seat |
| manager | 3 | `mgr1`–`mgr3` |
| staff | 12 | `staff01`–`staff12` |

Plus 40 published dresses with size variants and stock, 3 fitting rooms, 3
garment pieces, 28 future bookings and an 8-deep walk-in queue. Logins repeat
across tenants — `res.users.login` is unique per *database*, and one database per
boutique is the tenancy model.

**40 dresses, not 3.** `/floor/finish` is the most expensive call in the
campaign, and it is a full board rebuild *plus* an unbounded
`product.product` search over every published variant, whose whole result it
serialises into the response. At 3 dresses that search returns 12 rows and
disappears into the board's own cost — the call measures fast because the
fixture is trivial, which is not a finding about the server. 40 templates × 4
sizes = 160 variants makes the variant list the dominant term. Cost: the seed
step goes 4.6 s → 10.8 s, i.e. ~0.17 s a dress, taking a tenant end to end from
~9 s to ~15 s. `MODRYN_DRESSES` overrides it.

**Phones are `+972 52 TT VVVV`** — `TT` the tenant index, `VVVV` the VU index.
Deterministic on purpose: `MAX_SENDS_PER_HOUR = 3` counts rows created per phone
per rolling hour, so a re-randomised scheme would make a restarted stage look
like a rate-limit wall. Eleven digits, deliberately one short of a deliverable
Israeli mobile — see rule 1, and `assert_phone_scheme()`, which fails the seed if
that ever changes silently.

**Seeded bookings sit on the grid `/book` itself offers** — Sun–Thu, 10:00–17:00
Jerusalem local, on the hour — because `/book/submit` now refuses any other time
and `verify.sh` asserts the same against the rows. The grid is no longer constants: `seed_tenant.py` reads
`modryn.opening.hours` — the same model `_slots()` reads — and imports only
`DAYS_AHEAD` and `TZ` from the controller, so they cannot drift, and `gen_tenants.sh` re-asserts the *result* in
the same SQL `verify.sh` uses.

### One day is full on purpose

`/book` renders the waitlist form **only** for days where every hour is taken
(`full = not times` in `_slots()`, `t-if="full_days"` in the template). The
visitor journey's waitlist branch is 15% of that journey and ~13% of total
workload, and it opens by reading the day `<select>` off `/book`; with no options
it returns before the POST, so **not one waitlist assertion is recorded and the
k6 summary shows nothing missing.**

The old seed made that branch structurally dead, and the previous version of this
file codified it — `MODRYN_BOOKINGS` "must stay well under the grid size" — while
the seeder *raised* if bookings reached the grid size. The arithmetic:

| | |
|---|---|
| open hours per day | from `modryn.opening.hours`; seeded Sun–Thu 10:00–18:00 = 10..17 = **8** |
| controller window | offsets 1..14 → 14 days → exactly 10 Sun–Thu → **80 slots** |
| seed window | offsets 2..14 → 13 days → 9 or 10 Sun–Thu → **72 or 80 slots** |
| default bookings | 20, uniformly sampled |

Filling any *specific* day meant drawing all 8 of its hours out of 20 picks from
72: `C(64,12)/C(72,20)` = 1.05e-5, so 9.5e-5 across nine days. And that is not a
per-run dice roll — `random.seed('modryn-loadtest-<index>')` makes the draw fixed
per tenant index, so an index either produced a full day or never would. The
condition was not unlikely; it was excluded.

So `MODRYN_FULL_DAYS` (default **1**) fills whole days deliberately, then samples
`MODRYN_BOOKINGS` from what is left: 8 + 20 = **28 live bookings** on a 72-slot
grid, one full day out of nine. They are ordinary grid slots — same open weekday,
same hours, exactly on the hour — so `verify.sh` §"unoffered booking" still reads
0.

It takes the **last** open days in the window, not the first. Both render, but
the window slides forward with the clock while a gold snapshot does not: a day
seeded at offset 2 is "today" two days later, a day `/book` never offers, and
`verify.sh` then reports the seed's own rows as unoffered bookings. From the far
end the gold keeps ~12 days of shelf life instead of ~1.

Tuning: `MODRYN_MANAGERS`, `MODRYN_STAFF`, `MODRYN_DRESSES`, `MODRYN_FULL_DAYS`,
`MODRYN_BOOKINGS`, `MODRYN_QUEUE`. The seeder refuses if `MODRYN_FULL_DAYS` would
take every open day, or if `MODRYN_BOOKINGS` does not fit in what remains — in
either case `/book` would offer nothing and every booking POST would answer "just
taken".

## `tenants.json`

Gitignored: it names live logins. `MODRYN_DEMO_PASSWORD` is deliberately **not**
in it — a password in a config file is a password in a backup. The harness reads
it from its own environment.

```json
{
  "tenants": [
    { "slug": "lt01",
      "baseUrl": "http://lt01.localtest.me:8069",
      "staff": [{"login": "owner", "level": "owner"}, ...],
      "dressIds": [2, 3, 4],
      "phonePrefix": "+9725201" }
  ],
  "loadtestSecret": "…"
}
```

`*.localtest.me` resolves to 127.0.0.1, and `dbfilter = ^%d$` takes the first
hostname label as the database name — which is why slugs must be valid database
names *and* hostname labels.

### `origin`, and why the guard stopped trusting a hostname

`origin` is written once for the fleet, and `guardTenants()` **rebuilds** every
`baseUrl` from it (`<scheme>://<slug>.<host>`) and compares for equality rather
than pattern-matching. Export `BASE_SCHEME=https BASE_DOMAIN=$DOMAIN` and the
fleet is generated at `https://<slug>.$DOMAIN`.

That relaxation is not free, and it is worth being exact about what it cost. The
old `^http://<slug>\.localtest\.me:[0-9]+$` anchor was doing **two** jobs: it
proved `gen_tenants.sh` wrote the file, and it proved the target could not be a
boutique — because `new_boutique_prod.sh` serves boutiques at
`https://<slug>.$DOMAIN` and never on `localtest.me`. Launch gates 9 and 10 need
a *through-nginx* measurement, so the fleet had to move onto `$DOMAIN`, and the
second job is gone. **No shape rule brings it back**: `lt01` is a legal boutique
slug under `new_boutique_prod.sh`'s own grammar.

What replaces it is `/loadtest/ping`, called for **every** tenant from `setup()`
in `main.js` before any VU exists. It answers 200 only where this staging module
is installed, enabled, and holding the matching secret — a capability, not a
name, and one a production boutique cannot have because `loadtest/odoo_addons`
is not on production's `addons_path`. `/loadtest/otp` cannot serve as that probe:
every refusal there is deliberately the same 404, which is what makes it useless
as evidence.

## Running the campaign on the production box

**The whole campaign runs before the first real boutique exists.** This is the
decisive constraint and it costs nothing but ordering. Once the fleet lives on
the production domain, running load tenants alongside live brides is the one
arrangement where a single mistake writes invented customers onto a working
floor board mid-service. If no boutique exists yet, there is nothing to reach.

```
A  empty box: provisioned, template built, db_name empty,
   https://anything.$DOMAIN -> 404
B  load fleet -> ramp -> final validation ramp with LOADGEN_IP CLEARED
C  teardown, proven
D  real boutiques, with the rotated Twilio credentials
```

**Run k6 from an external generator, not on the box.** `modryn-http.conf`
exempts `127.0.0.1/32` from `limit_req` unconditionally, so an on-box generator
is structurally incapable of producing a 429 and makes launch gate 10 unfailable.
It also costs the measurement: 400 VUs plus TLS termination compete with 48 Odoo
workers and Postgres for the same 32 threads, so `rt` and `urt` would describe a
box running a load generator rather than one serving customers. External puts
RTT and jitter inside the numbers instead — subtract them the way
`modryn-http.conf` already says (`rt - urt` is queueing plus network, `urt` alone
is Odoo).

### Teardown proof

Absence-of-evidence dominates here, so each check needs a control. **Capture the
non-zero first**, during stage B, or a column of zeros is not evidence of
removal:

```bash
curl -sk "https://lt01.$DOMAIN/loadtest/ping?secret=$SECRET"   # {"loadtest":true}
```

Then, after dropping the fleet and restoring `odoo.service`'s `ExecStart`:

```bash
psql -lqt | cut -d'|' -f1 | grep -cE '^ *(lt[0-9]{2}|modryn_gold_seeded) *$'   # 0
ls /var/lib/modryn/filestore | grep -cE '^(lt[0-9]{2}|modryn_gold_seeded)$'    # 0

# ABSENT, not 'uninstalled' — and including modryn_template, which every future
# boutique is cloned from. A /loadtest/ping 404 proves nothing here: that route
# 404s for a wrong secret and a disabled flag too, by design.
for db in $(awk -F= '/^db_name/{gsub(/ /,"",$2);gsub(/,/," ",$2);print $2}' /etc/odoo/odoo.conf) modryn_template; do
  psql -d "$db" -tAc "select count(*) from ir_module_module where name='modryn_loadtest'"
done                                                                           # all 0

grep -c loadtest /etc/systemd/system/odoo.service /etc/odoo/odoo.conf          # 0 0
# The RUNNING process, not the unit file — the unit is what it will be next boot.
tr '\0' ' ' < /proc/$(systemctl show -p MainPID --value odoo)/cmdline | grep -c loadtest   # 0

# The exemption is gone — and the control that proves it, because an empty
# exemption file is also what a misconfigured provision.sh produces:
test ! -s /etc/nginx/modryn-loadgen-exempt.conf
sudo /opt/modryn/deploy/scripts/verify_edge.sh      # E4 must show 429s

rm -f loadtest/config/tenants.json
```

## Timings measured on this host

| job | measured | plan's budget |
|---|---|---|
| one tenant: clone + module install + seed | **~15 s** (~9 s of it before the catalog went 3 → 40 dresses) | ~29 s |
| `make_gold.sh` | ~2 s | — |
| `reset_tenants.sh`, per tenant | ~2 s | ~8 s |

The plan budgeted a separate "gold build" phase to install seven addons once,
because `modryn_template` had none. It has all seven now, so that phase is gone
and `gen_tenants.sh` clones straight from the template via `new_boutique.sh`.
At 15 s a tenant, 30 tenants is ~8 minutes serially and the plan's parallelism-4
is not worth the `createdb -T` contention.
